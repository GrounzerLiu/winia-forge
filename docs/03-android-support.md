# 03 · Android support

> Summary: Android does not require renaming the tool. The toolchain stays **Winia Forge / `winia` /
> `winia-cli` / `winia.toml`**, and Android joins as a target. The real work is in the winia framework's
> Android platform layer; the CLI only strings Gradle, NDK, adb, and signing together.

## 1. Command model

| Command | Android behaviour |
| --- | --- |
| `winia new my-app --platforms windows,macos,linux,android` | Generate the desktop + Android project skeleton |
| `winia platform add android` | Add the Android target to an existing project |
| `winia build --target android --release` | Compile the `.so` for each ABI, then hand off to Gradle for the APK |
| `winia run --target android --device <serial>` | Install, launch, wait for the result |
| `winia dev --target android` | Watch sources, recompile, reinstall, restart the Activity |
| `winia package --target android --format apk,aab` | Produce the installable package / store bundle |
| `winia sign --target android --keystore <file>` | Sign and verify |
| `winia doctor --target android` | Check SDK/NDK/JDK/adb |
| `winia devices` / `winia emulators` | Devices / emulators |
| `winia logcat` / `winia screenshot` | Logs and screenshots |
| `winia android init` / `sync` / `studio` | Android project initialisation / sync / open Android Studio |
| `winia ci init --platform android` | Generate Android CI |

Naming principle: a platform is `--target`, an artifact is `--format`; do not put Android in the tool name,
and do not put an artifact in a command name.

## 2. Generated project structure

```text
my-app/
├── Cargo.toml
├── winia.toml
├── assets/
│   └── icon.png
├── src/
│   ├── main.rs          # desktop entry point
│   ├── lib.rs           # Android entry point: android_main()
│   └── ui.rs            # UI shared by desktop and Android
└── android/
    ├── settings.gradle.kts
    ├── build.gradle.kts
    ├── gradle.properties
    ├── gradle/wrapper/
    └── app/
        ├── build.gradle.kts
        └── src/main/
            ├── AndroidManifest.xml
            ├── java/com/example/myapp/MainActivity.kt
            ├── res/
            │   ├── mipmap-*/ic_launcher...
            │   └── values/themes.xml
            └── jniLibs/          # generated at build time, not committed
```

### 2.1 Activity modes

| Mode | Characteristics | Use when |
| --- | --- | --- |
| `game` (GameActivity) | Has a Java/Kotlin Activity, supports soft-keyboard IME text events | Default; applications with a TextField |
| `native` (NativeActivity) | Pure native, no Java code needed | Simple graphics applications without text input |

GameActivity corresponds to winit's `android-game-activity` feature; NativeActivity corresponds to
`android-native-activity`. The two are mutually exclusive and cannot be enabled together.

### 2.2 Project file management

- `android/` is a generated directory, but users may add Kotlin/Java code and third-party SDKs.
- `winia android sync` only rewrites managed files: Gradle configuration, the Manifest, and resource
  skeletons.
- User code directories (`android/app/src/main/java/...`) are never overwritten.
- `winia android studio` opens `android/` directly so users can debug the native side in Android Studio.
- `local.properties` contains machine paths; it is written to `.gitignore` and generated by the CLI.

## 3. Android configuration in `winia.toml`

```toml
[android]
package = "com.example.myapp"
label = "My App"
min_sdk = 26
target_sdk = 36
compile_sdk = 36
activity = "game"              # game | native
version_code = 1
abis = ["arm64-v8a", "x86_64"]
orientation = "unspecified"    # portrait | landscape | unspecified
permissions = ["INTERNET"]
```

Notes:

- `min_sdk = 26` is the Skia Android build baseline (skia-bindings' Android platform module pins the API
  level to 26).
- `version_code` must increase monotonically; `winia release` can bump it automatically.
- `permissions` generates `<uses-permission>`; runtime permission requests come later through a JNI bridge.
- When `label` is empty, `app.name` is used.
- `package` defaults to `app.id` but can be overridden separately.

## 4. Build pipeline

### 4.1 Recommended approach: Gradle + cargo-ndk

```text
cargo ndk compiles the .so for each ABI
        ↓
copy into android/app/src/main/jniLibs/<abi>/
        ↓
Gradle assembleDebug / assembleRelease produces the APK
Gradle bundleRelease produces the AAB
```

Why the CLI does not assemble the APK itself:

- Gradle owns the AndroidManifest, resources, the R class, dependencies, Java/Kotlin, signing, and AAB;
  these are the de-facto standard of the Android toolchain.
- cargo-ndk owns Rust cross-compilation, the NDK linker, and the ABI directory layout.
- The CLI only selects ABIs, sets environment variables, invokes Gradle, collects artifacts, and reports
  errors.

```bash
winia build --target android --release --abi arm64-v8a,x86_64
```

Internally equivalent to:

```bash
cargo ndk -t arm64-v8a -t x86_64 -o android/app/src/main/jniLibs build --release --lib
cd android && ./gradlew assembleRelease
```

### 4.2 ABI mapping

| Android ABI | Rust target |
| --- | --- |
| `arm64-v8a` | `aarch64-linux-android` |
| `armeabi-v7a` | `armv7-linux-androideabi` |
| `x86_64` | `x86_64-linux-android` |
| `x86` | `i686-linux-android` |

Only `arm64-v8a` and `x86_64` are built by default: real devices are mostly arm64 and emulators commonly
use x86_64; armeabi-v7a is left for users who need older devices to enable explicitly.

### 4.3 Environment variables

- `ANDROID_HOME` / `ANDROID_SDK_ROOT`: SDK root.
- `ANDROID_NDK`: explicitly required by `skia-bindings`.
- `ANDROID_NDK_HOME`: used by `cargo-ndk`.
- `JAVA_HOME`: JDK 17 or 21.

`winia doctor --target android` must check all four variables and whether the SDK licenses have been
accepted.

### 4.4 Artifacts and alignment

- Debug APK: `android/app/build/outputs/apk/debug/app-debug.apk`.
- Release APK: `android/app/build/outputs/apk/release/app-release.apk`.
- AAB: `android/app/build/outputs/bundle/release/app-release.aab`.
- Android 15+ requires native libraries to support 16 KB pages: use NDK r27+ and run `zipalign -P 16`
  when packaging.
- On the first Android build, if no prebuilt Skia package is available, Skia is compiled from source and
  the build takes noticeably longer; `winia doctor` should point this out.

### 4.5 Fast path: cargo-apk2

`cargo-apk2` can bypass Gradle and produce a debug APK directly from Rust, which suits:

- Pure Rust demos without Java/Kotlin code.
- Quick validation of rendering and input.

It is not recommended as the official release path:

- AAB, Play signing, complex resources, and Java/Kotlin dependencies all end up requiring Gradle.
- Two build pipelines make problems harder to localise.

The CLI should default to Gradle and use cargo-apk2 only with `--pure-rust`.
cargo-apk2's manifest path produces a NativeActivity APK, so it cannot exercise the GameActivity
InputConnection or validate IME input. See [06-android-ime-and-apk.md](06-android-ime-and-apk.md).

## 5. Running and debugging

```bash
winia devices
winia emulators start --name Pixel_8_API_36
winia run --target android --device emulator-5554
winia logcat --filter com.example.myapp
winia screenshot --target android --output shot.png
```

### 5.1 `winia run`

- Build a debug APK.
- `adb install -r`.
- `adb shell am start -W` and wait for the launch result.
- On launch failure, print the most recent logcat automatically.
- `--release` runs the release package.

### 5.2 `winia dev`

- Watch `src/`, `assets/`, `Cargo.toml`, `winia.toml`, `android/app/src/`, and the Android Gradle
  files; build outputs are not registered.
- Build first, then recompile the device ABI's `.so`, reinstall the APK, force-stop the old process,
  and start the Activity. A failed build leaves the previous app running.
- Build failures keep the watcher alive and retry on the next edit.
- Debug builds enable `winia/debug-server`. Winia scans device ports from 9998; dev picks a free
  host port, reads the device port from logcat, and runs `adb forward tcp:<host> tcp:<device>` so
  `ws://127.0.0.1:<host>` reaches the app. The debug manifest
  (`android/app/src/debug/AndroidManifest.xml`) needs `android.permission.INTERNET`; the blank
  template includes it and existing projects must add it. `--once` keeps the forward after exit and
  prints how to remove it. Dev also writes app metadata to
  `files/winia-debug-info.json`; send `info` over the WebSocket to read it.
- This is a process-level hot restart, not code hot-swapping.

### 5.3 Logs and symbols

- `winia logcat` filters by package name by default and supports `--pid`, `--level`, `--clear`.
- `winia android symbols` extracts/keeps the debug symbols of `lib<app>.so`.
- Crash stacks are resolved with `ndk-stack` or `addr2line`.

## 6. Packaging, signing, and publishing

### 6.1 Artifact forms

| Artifact | Purpose | Command |
| --- | --- | --- |
| Debug APK | Local debugging, emulators | `winia run --target android` |
| Release APK | Sideloading, internal distribution | `winia package --target android --release --format apk` |
| AAB | Google Play upload | `winia package --target android --release --format aab` |
| Split APK | Smaller size per ABI | `winia package --format apk --split per-abi` |

### 6.2 Versions and signing

- `versionCode` comes from `winia.toml` or is bumped automatically by `winia release`; `versionName` uses
  semver.
- Debug builds use an automatically generated debug keystore.
- Release builds read signing material from environment variables, never from the repository:
  - `WINIA_ANDROID_KEYSTORE`
  - `WINIA_ANDROID_KEY_ALIAS`
  - `WINIA_ANDROID_KEYSTORE_PASSWORD`
  - `WINIA_ANDROID_KEY_PASSWORD`
- `winia sign --target android` wraps `apksigner` and verifies the signature.
- Supports Google Play App Signing: the upload key and the Play signing key are separate.

### 6.3 Verification

- `zipalign -P 16`: 16 KB page alignment.
- `apksigner verify --print-certs`: signature verification.
- `bundletool validate`: AAB validation.
- `aapt2 dump badging`: package name, version, and targetSdk checks.
- Generates SHA256 checksums and an artifact manifest.

### 6.4 Icons and store assets

- Adaptive icons: `res/mipmap-anydpi-v26/ic_launcher.xml` + foreground/background layers.
- Density icons: mdpi, hdpi, xhdpi, xxhdpi, xxxhdpi.
- Play Store icon: 512×512 PNG.
- Splash Screen (Android 12+): optionally generated.
- Later: placeholder resources for Play Store screenshots and the feature graphic.

## 7. Android-specific features

### 7.1 Permissions and Manifest

- `[android] permissions` generates `<uses-permission>`.
- Runtime permission requests need a JNI bridge; the first version can declare permissions only.
- `android:exported`, `launchMode`, `configChanges`, and similar are generated uniformly by the template;
  users do not edit them by hand.

### 7.2 Lifecycle and state restoration

- Activity `onCreate` / `onResume` / `onPause` / `onDestroy` map to winia's `ApplicationHandler`.
- On rotation, background kill, or Activity recreation, `remember_saveable` state is restored through the
  `Bundle`.
- The back button maps to winia's back/close-overlay behaviour.
- Restoration after process death is a P3 capability.

### 7.3 Insets

- Status bar, navigation bar, notch, gesture bar, and soft-keyboard height are written into
  `WindowInsetsController`.
- The real values must be read from `AndroidApp::content_rect()` and the JNI `WindowInsets`.
- Android density comes from winit's scale factor; the `Dp` system can be used directly, but needs
  verification.

### 7.4 IME and text input

This is the most critical blocker for Android support:

- Upstream winit 0.31.0-beta.4's Android backend only handles MotionEvent/KeyEvent; `InputEvent::TextEvent`
  and `TextAction` are dropped.
- `android-activity 0.6.1`'s GameActivity already provides `TextEvent` / `TextAction` /
  `text_input_state()`.
- The Winia fork translates those events into `WindowEvent::Ime`; its published packages are
  `winia-winit` (library name `winit`) and `winia-winit-android`.
- NativeActivity has no `InputConnection` and cannot realistically do soft-keyboard text input; TextField
  therefore requires GameActivity.
- See [06-android-ime-and-apk.md](06-android-ime-and-apk.md) for the build configuration, lifecycle failures,
  and verification procedure.
- The original research record lives in the Mnemon document "winit Android IME support research and refactor
  plan (0.30.13 / 0.31.0-beta.4, GameActivity)".

### 7.5 Clipboard

- `arboard` has no Android backend; winia's current `arboard::Clipboard` calls do not compile on Android.
- `arboard` must move to non-Android target dependencies, and Android needs a JNI `ClipboardManager`
  implementation for reads.
- Writes can go through winit's `set_clipboard` first.

### 7.6 Assets and fonts

- Android assets are read through `AndroidApp::asset_manager()`.
- The template's `assets/` is packaged into the APK.
- winia's image/font loading needs an AssetManager path.
- Fonts embedded with `include_bytes!` (such as Material Symbols) are unaffected.

### 7.7 Accessibility

- The Windows UIA bridge does not apply to Android.
- TalkBack needs `AccessibilityNodeProvider` or a Jetpack Compose-style semantics-tree bridge.
- The work is substantial; schedule it after Android is stable.

### 7.8 Desktop-only behaviour

- Scrollbars, hover, mouse wheel, and context menus do not apply on Android; templates and components
  should hide or degrade automatically.
- Android is a single-window model; `Window::new()` multi-window must not be exposed.

## 8. Framework prerequisites

The paths below are all in the `D:\Projects\winia` repository.

| Item | Current state | What is needed |
| --- | --- | --- |
| winit Android backend | `winia/Cargo.toml` only has `winit = { workspace = true }`; the Android feature is not enabled | Pass through `android-game-activity` / `android-native-activity` |
| Application entry | `winia/src/app.rs`'s `run_app` calls `EventLoop::new()` directly | Add `run_app_android(app: AndroidApp, ...)` using `EventLoopBuilderExtAndroid::with_android_app` |
| `run_app!` macro | `winia-macros/src/lib.rs` expands to a plain `app::run_app` expression | Add `android_main!` or have the template generate `#[no_mangle] fn android_main` |
| Skia build | The Windows target explicitly enables `textlayout/svg/gl/vulkan`; the Android target has no equivalent | Add Android `skia-safe` feature configuration; `skia-bindings` requires `ANDROID_NDK` and API level 26 |
| Clipboard | `arboard` has no Android platform module | Conditional compilation + a JNI ClipboardManager |
| Window API | `winia/src/app/window.rs`'s builder only has `title/size/on_close` | Add fullscreen, orientation, status bar, icon, and other mobile attributes; restrict to a single window |
| Insets | `winia/src/window/insets.rs` describes itself as desktop-shaped and has no Android data source | Wire up `AndroidApp::content_rect`, IME insets, status bar, and navigation bar |
| IME | The Winia winit fork forwards `TextEvent` / `Commit` / `DeleteSurrounding`; published as `winia-winit` + `winia-winit-android` | Use GameActivity; the native library entry and lifecycle hooks are documented in 06-android-ime-and-apk.md |
| Lifecycle | No handling for Android Activity recreation | Map `suspended/resumed`; write `SaveableStateRegistry` into the Bundle |
| Input | winit has touch events, but gestures need verification | Test the `PointerEvent` touch path; add long-press/swipe/double-tap |
| Debug channel | `winia/src/app.rs` starts `start_stdin_channel()` | Android has no stdin; skip it under cfg and keep only the WebSocket |
| Assets | winia mostly uses file paths today | Add AssetManager reads |
| Accessibility | Windows UIA only | Implement the Android semantics bridge later |

### 8.1 Rendering feasibility

After a preliminary review of the dependency sources, the rendering layer is more complete than expected:

- `softbuffer 0.4.8` already has an Android backend (`skiwin/src/cpu.rs`'s CPU path can work).
- `glutin 0.32.3` supports Android EGL; `skiwin/src/gl/context.rs` takes the EGL branch on non-Windows/macOS
  platforms.
- `vulkano 0.35` supports `VK_KHR_android_surface`.
- `skia-bindings 0.99` has an Android platform build module.

Conclusion: the first version can use **GL + softbuffer as the fallback**, with Vulkan as an optional path;
there is no need to tackle Vulkan from the start.

## 9. Roadmap

Detailed acceptance criteria are in [05-roadmap.md](05-roadmap.md). The Android order:

1. **P0 feasibility check**: winit Android entry point, single window, touch, GL/softbuffer rendering,
   a manually produced hello-world APK.
2. **P1 CLI MVP**: `winia new --platform android`, `doctor`, `build/run`, `devices/logcat`, debug APK.
3. **P2 release pipeline**: icons, insets, basic lifecycle, `package --format apk,aab`, signing, 16 KB
   alignment, CI templates.
4. **P3 full capability**: IME (winit fork), clipboard, assets, saveable, permissions,
   `test --target android`.
5. **P4 ecosystem**: TalkBack accessibility, Play publishing, emulator automation.

Effort estimate: the CLI's Android wrapper is the small part; the bulk is the framework's Android platform
layer (window, rendering, lifecycle, IME).

## 11. Naming conclusion

- Continue using **Winia Forge / `winia` / `winia-cli` / `winia.toml`**.
- Do not add platform-specific names such as `winandroid` or `winpack-android`.
- Android is only a target; platform differences are expressed through `--target android` and
  `winia android ...`.
